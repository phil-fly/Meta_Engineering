# Workflow Contracts

本文件是本技能工作流（WF）与横切协议（CX）的唯一权威定义。`SKILL.md` 只保留路由表与触发词索引；修改任一 WF 或 CX 时只改本文件。

## 编号体系

| 前缀 | 含义 | 成员 |
| --- | --- | --- |
| WF-M | 主干工作流，顺序执行，可停在任意环节 | WF-M1 ~ WF-M5 |
| WF-T | 任务型工作流，可独立触发，完成后回填主干 | WF-T1 ~ WF-T3 |
| WF-G | 出口门，全技能唯一 | WF-G1 |
| CX | 横切协议，不占主干，在标注步骤生效 | CX-1 ~ CX-5 |

## 协作强度（L0 入口路由）

每次会话先判定协作强度，判定顺序固定为：先看是否把交付物作为本轮产出物索取，再看是否需要长期记忆，最后才看是否要求落盘。协作强度只决定读写行为（是否读记忆、是否落盘），不改变 WF 内容；场景由 WF 路由决定，两维正交。

| 模式 | 触发 | 行为 |
| --- | --- | --- |
| 轻量讨论 | brainstorm、快速判断、局部问题，或仅提及交付物名词做方法咨询（如“PRD 该怎么写”） | 直接讨论；不初始化 `ai-agent-workspace/product/`，旧 `docs/` 项目同样不初始化 |
| 产物沉淀 | 把 PRD、立项、设计说明、mockup、调研报告等作为本轮产出物索取（如“写个 PRD”“出个线稿”），或要求生成文件 | 按本档交付完整内容；“先别写文件”只停止落盘，不降低完整度；先确认目标文件或建议目录 |
| 项目记忆模式 | 长期项目、多轮协作、用户要求记住决策，或已存在 `ai-agent-workspace/product/memory/` / `docs/00_MEMORY/` | 读取项目记忆、`CONFIRMATIONS.md`（存在时），并在交付前运行确认记录校验 |

读写权限按模式严格区分：

- `轻量讨论`：只产生会话内结论，不写入任何项目文件。
- `产物沉淀`：只写入用户要求的交付物（PRD、立项、设计说明、mockup、调研报告等），不自动写入长期记忆。
- `项目记忆模式`：按 CX-3 和记忆协议维护项目记忆；DECISIONS 必须有用户明确确认依据。

## WF 注册区

每个 WF 统一五段式定义：触发 / 输入（继承上游）/ 步骤 / 输出与可写文件 / 退出条件。

### WF-M1 价值发现

- 触发：用户带来想法、痛点或目标用户线索，进入产品价值讨论。
- 输入：无上游依赖，会话入口即进入。
- 步骤：
  1. 先让用户自由讲述，不用长清单过早框住思路。
  2. 追问真实故事、目标用户、约束、替代方案和不可忍受的摩擦。
  3. 提炼一个可观察的价值锚点，例如时间、成本、步骤、风险、心理负担或业务指标变化。
  4. 有具体故事或硬约束时，仅在项目记忆模式下追加到产品记忆目录的 `CONTEXT_SNAPSHOT.md`；其余模式只在会话内记录，不写入文件。
  5. 价值、范围、目标用户逐步清楚后，仅在产物沉淀（用户索取立项文档）或项目记忆模式下维护产品策略目录里的立项类文档。
- 输出与可写文件：价值锚点、目标用户、痛点、替代方案、待确认项；可写文件受协作强度约束——仅项目记忆模式可写 `ai-agent-workspace/product/memory/`，仅产物沉淀或项目记忆模式可写 `ai-agent-workspace/product/strategy/`，兼容 `docs/00_MEMORY/`、`docs/01_STRATEGY/`。
- 不可写条件：用户仍在自由讲述且未确认方向。
- 退出条件：至少一个价值锚点被用户确认。

### WF-M2 流程与范围

- 触发：价值锚点已确认，进入范围与 MVP 讨论。
- 输入：必须继承 WF-M1 的价值锚点，不能脱离原痛点重写目标。
- 步骤：
  0. 过 CX-1 领域约束识别门；时间点、日期、时长、时间范围、时区、超时或过期语义命中时读取时间路由并回填旅程和验收约束。
  1. 从痛点出发写 3-5 条关键用户旅程。
  2. 先画理想端到端流程，再切 MVP。
  3. MVP 用“支持哪些旅程”定义，不用孤立功能清单定义。
  4. 每个核心旅程都记录 `{入口场景} -> {可见信息} -> {用户动作} -> {结果}`。
  5. 仅在项目记忆模式下，或产物沉淀模式且 Framework PRD 本身属于用户要求的交付物时，写入或更新产品 PRD 目录的 `framework-prd.md` 或项目约定的 Framework PRD；用户只要求设计说明、mockup 等其他交付物时，不自动生成或更新 Framework PRD；轻量讨论只在会话内输出旅程与范围结论。若需求涉及 UI，同步沉淀页面设计需求与低保真线稿，信息不足时写入稳定待定项；若不涉及 UI，标注页面设计与线稿不适用。
- 输出与可写文件：关键用户旅程、MVP 支持/延后范围；可写文件受协作强度约束——仅项目记忆模式可写 `ai-agent-workspace/product/memory/TODO.md`，仅产物沉淀（Framework PRD 属用户要求的交付物时）或项目记忆模式可写 `ai-agent-workspace/product/prd/framework-prd.md`，兼容 `docs/02_PRD/`、`docs/TODO.md`。
- 不可写条件：痛点未闭环或范围仍明显发散。
- 退出条件：痛点覆盖关系和 MVP 延后项都被明确记录。

### WF-M3 交互结构

- 触发：核心旅程和 MVP 边界已确认，且需求涉及 UI。
- 输入：必须继承 WF-M2 的关键用户旅程；UI 相关需求必须在实体定义（WF-M4）前沉淀页面设计需求和低保真线稿，不能只写功能清单或后台逻辑。
- 步骤：
  1. 定义 Screen Tree、信息层级、主操作和关键入口。
  2. 把 WF-M2 的旅程映射到页面结构。
  3. 为 UI 相关核心页面生成可评审的低保真线稿，并标注内容区块、主操作、状态和导航关系。
  4. 以目标用户视角走查：是否看得懂、知道下一步、能回到上下文。
  5. 发现冲突时调整页面结构并记录重要设计转向。
- 输出与可写文件：Screen Tree、页面设计需求、低保真线稿、信息层级、主操作；Framework PRD 或 `ai-agent-workspace/product/design/ui_ux/`，兼容 `docs/03_DESIGN/ui_ux/`。
- 不可写条件：旅程还未稳定，或需求不涉及 UI。
- 退出条件：UI 相关核心旅程在页面结构中都有明确落点，关键页面均有设计需求和线稿或稳定待定项。

### WF-M4 实体定义

- 触发：UI 需求页面结构和关键操作已确定；非 UI 需求业务流程和关键操作已确定。
- 输入：按需求类型条件继承——UI 需求继承 WF-M2 的业务流程和 WF-M3 的页面结构；非 UI 需求（纯后台、API、数据处理、平台、权限策略等）继承 WF-M2 的业务流程及关键操作，跳过 WF-M3 直接进入实体定义。
- 步骤：
  0. 在实体和字段定义前过 CX-1 领域约束识别门；命中时间点、日期、时长或时间范围字段时先确认时间语义和时区来源，再决定字段类型与验收边界。
  1. 从业务流和页面结构抽象实体，不先写数据库 schema。
  2. 对关键实体按状态机处理：状态含义、可见性、可编辑性、正向/反向/跳跃转移、每状态操作、字段行为。
  3. 用实体模型回查页面结构，发现缺字段、假关系、无 UI 状态或无实体承载的动作时及时调整。
- 输出与可写文件：实体清单、状态机、操作矩阵、字段行为；Framework PRD 或 Feature PRD。
- 不可写条件：UI 需求页面结构尚未成形，或非 UI 需求业务流程与关键操作尚未明确。
- 退出条件：UI 需求用户流、前端页面、后端逻辑三层都能对齐；非 UI 需求业务流程与实体状态机、操作矩阵对齐。

### WF-M5 设计与交付

- 触发：交互结构、实体状态、设计方向已确认。
- 输入：必须继承已确认的交互结构、实体状态和待定项结论；已有产品或目标仓还必须先继承生产 Token、主题、组件、布局和响应式真值源，不得平行新建一套设计参数。
- 步骤：
  1. 设计产物默认放在产品设计目录，生产代码只在设计确认后再改。
  2. 高保真前先写设计指导文档，标记并解释 `[待定项-XXX]`。
  3. mockup 使用自包含 HTML；确认后补充 handoff note。
  4. 视觉与交付细节按 `references/design-artifacts.md` 和 `references/design-handoff.md` 执行。
- 输出与可写文件：设计指导、mockup、handoff note；`ai-agent-workspace/product/design/`，兼容 `docs/03_DESIGN/`。
- 不可写条件：待定项影响页面结构或实体逻辑。
- 退出条件：设计稿、待定项、交付说明和后续开发入口清楚。

### WF-T1 PRD 编写

- 触发：用户要求写 PRD、生成 PRD、补 PRD，或把需求整理成可开发文档。
- 输入：可从 WF-M2/M3/M4 的产出切入，也可独立接收用户输入；独立编写时不跳过领域约束识别。读取 `references/prd-protocols.md`。
- 步骤：
  0. 需求涉及数据、API、配置、权限、时间、导出、部署、性能或安全语义时，先过 CX-1 领域约束识别门，把约束映射进旅程、实体和验收语义。
  1. 起草前先按 Input Classification 标注关键输入，按 Depth Selection 说明深度与依据。
  2. 判定需求是否涉及 UI、页面、交互、导航、前端状态或用户可见体验。
  3. 涉及时，Framework PRD 和 Feature PRD 必须包含页面相关设计需求与低保真页面线稿：Framework PRD 在 Screen Tree 后覆盖关键页面的用途、内容区块、状态、主操作和导航，并给出核心流程线稿；Feature PRD 在 Frontend Specs 中覆盖受影响页面、组件层级、状态/空态/错误态、权限可见性和对应线稿。
  4. 纯后台、API、数据、平台、权限策略或内部流程等不改变用户界面的 PRD 不强制生成线稿，应在页面设计小节标注 `N/A` 或说明不适用原因。
  5. UI 信息不足时用稳定 `[待定项-XXX]` 说明缺口、影响和需要用户决定的问题，不得直接省略。
- 输出与可写文件：Framework PRD 或 Feature PRD；落盘位置由协作强度决定（产物沉淀/项目记忆模式时写入对应 PRD 目录）。
- 不可写条件：无（落盘行为由协作强度决定）。
- 退出条件：若需求涉及 UI，关键用户旅程均落到页面，关键页面均有设计需求和低保真线稿，或有明确待定项说明为什么暂不能画；若不涉及 UI，已明确标注页面设计与线稿不适用；并在交付前通过 Delivery Final Checks。

### WF-T2 PRD 评审

- 触发：用户要求 review、评审、找问题、补 PRD、看需求是否可开发。
- 输入：PRD 文本或文件路径；读取 `references/prd-protocols.md` 的 PRD Review Protocol。
- 步骤：
  1. 读取目标文档或片段，输出 `Blocker`、`Clarification`、`Suggestion`。
  2. 用户确认后再改文档；可选择原地修改、新版本文档或只给评论。
- 输出与可写文件：blocker、clarification、suggestion、可执行性判断；原 PRD 或新版本 PRD。
- 不可写条件：未读目标文档或用户只要求口头反馈。
- 退出条件：所有发现都按 CX-5 归入闭环状态（已解决、延后处理、明确排除、转入后续任务）。

### WF-T3 竞品调研

- 触发：用户要求查竞品、市场替代方案、benchmark、类似产品或验证有没有现成解法。
- 输入：目标问题、市场/用户范围；读取 `references/research-and-competition.md`。
- 步骤：
  1. 先明确调研问题和目标用户。
  2. 查证或整理 3-5 个替代方案。
  3. 只把竞品转化为需求启发，不直接照搬功能；明确“不采纳项”和原因。
- 输出与可写文件：替代方案矩阵、证据、启发与不采纳项；`ai-agent-workspace/product/resources/`，兼容 `docs/04_RESOURCES/`。
- 不可写条件：无联网能力且用户未提供资料。
- 退出条件：形成替代方案矩阵，结论回填 WF-M1 的价值锚点或 WF-M2 的范围判断，不作为孤立资料堆积。

### WF-G1 定稿与最终交付（唯一出口）

- 触发：用户明确要求定稿、输出最终版、开发交付、handoff、提 PR 或生成 PR 标题/描述，且唯一目标 `Scope/Version` 可确定。
- 输入：必须继承已确认当前状态和实际变更，不得从对话历史重新生成需求范围，不得把 diff 当作需求来源，也不得把讨论时间线直接改写成最终文档；先读取 `references/final-state-delivery.md`，锁定唯一目标 `Scope/Version` 并区分需求交付与实现交付。
- 步骤：
  1. 当前对话中对象、范围和结论明确的用户指令优先；项目记忆模式下，已有记录先校验基线再追加本轮完整快照并复验，空注册表先写首条 `add` 再校验，然后运行 `scripts/validate-confirmations.py --project <project-root> --scope <scope_id@version> --json` 投影当前状态。两份确认注册表同时存在时停止并处理 split-brain；无注册表且必须依赖旧产物时才运行 `scripts/validate-legacy-current.py`。
  2. 在写入需求、验收标准、任务或代码前，对 Agent 提出的新增能力执行需求准入；未获明确接受的能力保持 `proposed`。
  3. 删除或隔离被拒绝、已替代、已解决批注、划线旧文和 Agent 执行过程；通过准入的版本边界与长期边界除外。
  4. 仅在用户要求实现交付时读取 `references/implementation-delivery.md`、diff 与验证结果。产品范围变更必须映射到当前需求；行为保持的实现支撑变更必须映射到被支撑需求、diff 和验证结果。
  5. 分开输出需求状态和实现状态；没有实现证据时，需求可以 Ready，但实现保持 `Not assessed`。
- 输出与可写文件：干净的当前状态 PRD、handoff 或交付摘要；需求状态与实现状态分开报告；当前权威 PRD、设计、handoff；用户要求时可生成 PR 文案。
- 失败路径：目标范围不明、确认源 split-brain、状态链校验失败或 legacy-current 标记不合规时停止对应范围定稿并标记 `unresolved`；无法读取实际变更或验证结果时可以完成需求 handoff，但实现保持 `Not assessed`。
- 退出条件：最终产物只包含当前已确认状态、用户确认的当前版本 Out/Deferred 和仍影响实现的待定项；未映射需求声明、未验证实现声明和未经准入的过程残留均为 0；需求标记 `Ready for development` 时 blocking pending 为 0 且无当前状态冲突；只有读取实现证据并通过验证后，才能把实现标记为 `Verified`；所有历史残留均已删除、隔离，或逐项通过排除项准入门。

## 横切协议（CX）

横切协议不占主干节点，在标注步骤生效。

### CX-1 领域约束识别门

生效点：WF-M2 步骤 0、WF-M4 步骤 0、WF-T1 步骤 0。

需求讨论工作流负责把用户目标推进为可确认的旅程、范围、实体、接口和验收语义。它不把具体工程规则复制到用户级或项目级协议，而是在领域约束识别门按需查找当前生效协议的工程路由。

在需求涉及数据、API、配置、权限、时间、导出、部署、性能或安全语义时：

1. 先识别命中的领域和需求边界，不因为关键词出现就假设实现方案。
2. 按当前生效协议的工程路由索引查找真实路由，再读取对应规则正文和检查项；禁止把通用领域规则复制到本技能或项目协议。若当前协议没有可解析的真实路由，必须标为待确认并限制结论，不得凭经验补写规则。
3. 将命中的约束映射回需求字段、用户旅程、实体状态、接口契约、验收标准或待确认项。
4. 需求阶段只确认业务语义和约束影响；实现命令、框架细节和项目私有配置留给开发或项目规范流程。
5. 最终输出说明命中的领域路由、已覆盖约束、未覆盖范围、明确排除项和剩余风险。

时间需求特别触发当前工程路由索引中的 `core/time-and-timezone.md`：先区分 Instant、Date 和 Duration；时间范围分别定义端点语义、开闭区间与空值语义，再定义存储、API、展示、导出、计算和测试边界。

### CX-2 UI 线稿门

生效点：WF-T1 起草前、WF-M2 步骤 5、WF-M3 全程。

规则正文见 `references/prd-protocols.md` 的 UI-Related Page Design Requirements & Wireframes Gate。要点：需求涉及 UI、页面、交互或前端体验时，PRD 必须同步覆盖页面设计需求与低保真线稿；不涉及 UI 时标注 `N/A` 或说明原因；无法判断时标注待定项。

### CX-3 记忆与确认链

生效点：项目记忆模式全程、WF-M1 项目记忆写入时、WF-G1；产物沉淀模式只写入用户要求的交付物，不触发长期记忆写入。

- DECISIONS 只能来自用户明确确认；TODO 可以来自不确定项，但必须标注触发原因。
- 对同一 `Requirement ID + Scope/Version`，确认记录必须形成线性快照链，最新记录是唯一通过校验的 `active`；旧 Context、Session、批注和旧版本只作为证据，不得反向覆盖当前状态。链校验失败、目标范围不明或替代关系不清时必须询问。
- 记忆结构、写入阈值与初始化协议见 `references/memory-system.md`；当前状态投影规则见 `references/final-state-delivery.md`。

### CX-5 闭环状态

生效点：WF-T2、WF-T3 以及一切审查、调研或需求整理产生发现项时。

审查、调研或需求整理产生的问题必须归入以下状态之一：

- 已解决
- 延后处理
- 明确排除
- 转入后续任务

不要让发现项在后续编辑或总结中消失。

这里的“不消失”是指每个发现都要有闭环状态并留在评审记录、TODO、决策记录或版本历史中，不是要求把已拒绝方案和纠正过程保留在最终 PRD 或交付摘要中。
