## 项目约束

本节只写仓库专属约束。通用工程约束应维护在 `ai-agent-protocols/routes/`，业务能力、接口、数据结构、配置、权限模型或系统架构约束应优先维护在项目 Spec、OpenSpec、ADR 或设计文档。OpenSpec 工作流应由目标仓已选 Spec 或场景手册入口承载，不在本协议重复展开。

约束摄入规则：

```text
长期项目事实/约束 → 本项目协议
工程通用规则  → ai-agent-protocols/routes/
任务执行流程  → 已选场景手册真值源（默认 ai-agent-protocols/playbooks/）
审查验收清单  → ai-agent-protocols/checks/
业务规范      → Spec / OpenSpec / ADR / 设计文档
生成过程证据  → 生成报告 / 任务日志 / Issue / PR 描述
```

不要把 `已验证项目事实来源`、读取文件清单、扫描过程或临时证据作为长期章节写入本协议；如需交付这些信息，应放在生成报告或任务记录中。

每条项目约束至少按以下结构记录，不要只写一个词、一个模块名或一句空泛口号：

```text
约束名称：
适用范围：
生效条件：
规则正文：
验证方式：
例外/优先级：
```

填写要求：

- `约束名称` 使用稳定短语，便于检索和复用。
- `适用范围` 写明目录、模块、环境、角色或任务类型。
- `生效条件` 写明何时适用；始终适用时写 `默认全局`。
- `规则正文` 应使用稳定规范词；只有已验证且长期适用的项目事实可使用 `必须`、`禁止`、`默认` 或 `仅当`，证据不足或跨项目通用内容应写为 `应`、`建议` 或 `如项目采用...`。
- `验证方式` 写明命令、检查项、测试、代码审查点或运行证据。
- `例外/优先级` 没有例外时写 `无`；有上层覆盖时写明来源。
- 若约束已在后文详情章节、场景手册、检查清单或工程路由展开，本节只保留锚点引用和项目差异，不重复展开同一规则正文。

建议按以下类别收集项目约束，但每类仍应按上面的结构展开：

## 风险与验证约束

默认按变更风险选择验证强度：

```text
低风险    → 相关单测 / lint / 局部构建
中风险    → 相关单测 + 集成或端到端关键路径
高风险    → 影响分析 + 方案确认 + 回归验证
```

最终回复应说明：

- 已运行的验证命令和结果。
- 未运行的验证及原因。
- 剩余风险或需要人工确认的事项。

以下变更默认视为高风险：

- 身份认证
- 权限控制
- 数据迁移
- 删除操作
- 安全控制逻辑
- 支付、账务、审计、合规或生产配置
- Git 历史改写、批量删除、不可逆脚本

高风险变更应先说明影响范围、回滚方式和验证方式，再实施。

如本节已定义风险分级，项目约束列表中只引用本节锚点，不重复列出同一高风险清单。

## Git 原则

默认不自动提交。

仅在以下情况提交：

- 用户明确要求。
- 项目协议明确要求。

提交范围仅包含当前任务相关内容；不要把无关格式化、重命名或临时文件混入提交。

## 交付要求

最终回复应包含：

- 变更摘要。
- 验证结果。
- 未覆盖范围。
- 剩余风险或后续建议。
