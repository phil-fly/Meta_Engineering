# 场景手册

本文件是技能内场景流程的单一来源。落盘到目标仓时，先确认场景手册真值源：新项目默认使用 `ai-agent-workspace/protocols/playbooks/` 并按章节拆分为独立文件；旧项目可兼容 `ai-agent-protocols/playbooks/`。若目标仓已有根级 `playbooks/` 并明确继续作为真值源，则协议包内只生成索引或别名说明，不复制完整正文。

## WF-CODING coding

开发任务默认流程：

1. 预检门：识别语言、工程域、风险等级和约束触发项；至少检查是否命中规范同步、最小修改、项目命令、权限/安全、数据迁移、删除、配置、性能、日志、用户可见文案、架构边界、Git 和知识沉淀相关 `CON-*`。
2. 路由门：先读 `../engineering/index.md`，再读取对应工程路由；涉及运行配置、功能配置或外部集成配置时，必须读取配置可发现性规则；涉及安全、错误日志、国际化、通用质量或性能时，分别补读 `../engineering/security/index.md`、`../engineering/core/error-and-logging.md`、`../engineering/frontend/i18n-governance.md`、`../engineering/core/common-quality.md` 或 `../engineering/performance/index.md`。
3. 变更门：涉及 API、数据结构、配置、权限模型或系统架构时，先确认项目规范、OpenSpec、ADR 或设计文档是否需要同步；命中高风险项时先说明影响范围、回滚方式和验证方式；按最小修改实施。
4. 验证门：运行与变更范围和风险等级匹配的验证；验证不可用时说明原因、替代证据和剩余风险。
5. 报告门：汇报变更、命中的关键约束、验证结果和剩余风险；若涉及协议维护或规则变更，按 `../checks/checklists.md` 的 `CHK-MAINT-*` 闭环；若产生可复用经验、长期设计模式或架构决策，先询问用户是否沉淀到 Wiki。

## WF-ARCHITECTURE architecture

架构任务默认流程：

1. 预检门：明确目标、约束、非目标、影响范围和约束触发项；涉及 API、数据结构、配置模型、权限模型或系统架构时，先进入规范同步判断。
2. 路由门：读取相关工程路由和通用质量、安全、性能路由；涉及认证、授权、数据迁移、删除、安全控制、生产配置或不可逆操作时补读安全或风险相关路由。
3. 设计门：对比可选方案及权衡；命中高风险约束时说明影响范围、回滚方式、兼容策略和验证方式。
4. 报告门：给出推荐方案、迁移影响、验证方式、命中的关键约束和剩余风险；若产生可复用经验、长期设计模式或架构决策，先询问用户是否沉淀到 Wiki。

## WF-ENTERPRISE-SAAS-DESIGN enterprise-saas-design

企业级 SaaS、安全产品、管理后台、控制台、运维平台、安全平台、云管平台、AI 平台、数据平台或设备管理系统的产品与页面设计默认流程：

1. 预检门：判断任务是否属于企业级产品设计；官网、活动页、品牌宣传、营销落地页、游戏化界面或纯概念稿不使用本流程。
2. 路由门：读取 `../engineering/frontend/enterprise-saas-design.md`，并按页面类型补读紧凑布局、UI 稳定性、组件系统、表格列表、表单、Design Token、可访问性和测试相关路由。
3. 建模门：完成产品建模，至少输出系统类型、核心实体、用户角色、核心流程、辅助流程、关键状态和用户真正管理的对象。
4. 信息架构门：按用户目标、业务流程和业务领域组织一级菜单、二级菜单、菜单职责、用户入口和核心操作。
5. 页面定义门：为每个关键页面定义页面目标、主要操作、次要操作、管理实体、关键决策、前置条件和后置结果。
6. 设计门：根据页面职责推导布局和组件，覆盖 Dashboard、管理页面、编辑页面、巡检中心或项目特定页面结构。
7. 交付门：先输出线框图，再输出视觉设计 Prompt 或高保真设计稿；用户明确只要局部产物时，保留必要前置结论并说明省略项。
8. 验证门：使用 `../checks/checklists.md` 的 `frontend-enterprise-saas-design-checklist` 验收，说明已覆盖项、未覆盖项和剩余风险。

## WF-SECURITY-REVIEW security-review

安全审查默认流程：

1. 预检门：声明审查模式、范围、未覆盖范围、资产边界和约束触发项；识别认证、授权、资源归属、敏感数据、审计、配置、外部依赖、删除和不可逆操作。
2. 路由门：读取 `common-security.md`、`auth-and-permission.md`、相关语言路由和相关业务路由；涉及配置或历史实现检查时补读 `dependency-and-config.md`；如项目协议声明专用影响面工具，优先用于盘点入口、数据流、身份、资源、敏感操作和外部依赖，不可用时说明限制并用源码搜索、日志或测试结果替代。
3. 证据门：先盘点入口、数据流、身份、资源、敏感操作、外部依赖和配置入口。
4. 分析门：按控制点审查，避免只凭漏洞直觉搜索；发现问题时关联对应 `CON-*` 或 `CHK-SEC-*`。
5. 验证门：按 `../checks/checklists.md` 的 `CHK-SEC-*` 自检后，输出发现、证据、影响、修复建议、命中的关键约束、未覆盖范围和沉淀去向。

## WF-PERFORMANCE-REVIEW performance-review

性能审查默认流程：

1. 预检门：声明审查范围、关键路径、性能目标和约束触发项；识别数据访问、缓存、资源生命周期、并发、阻塞、前端体积或渲染风险。
2. 路由门：读取 `common-performance.md`、相关语言路由、数据访问和可观测性路由；如项目协议声明专用影响面工具，优先用于盘点关键路径、调用链、数据访问和外部依赖，不可用时说明限制并用源码搜索、日志或测试结果替代。
3. 分析门：检查 N+1、资源泄漏、复杂度、对象分配、阻塞和缓存一致性，并关联对应 `CON-*` 或 `CHK-PERF-*`。
4. 验证门：按 `../checks/checklists.md` 的 `CHK-PERF-*` 自检后，输出瓶颈、证据、优化建议、验证方式、命中的关键约束和风险。

## WF-TROUBLESHOOTING troubleshooting

故障排查默认流程：

1. 预检门：明确现象、影响范围、发生时间、复现条件、最近变更和约束触发项；若项目协议声明本地调试记忆文件，先读取该文件获取固定调试环境信息。
2. 证据门：收集日志、错误信息、配置、输入输出、环境差异和相关代码证据；涉及敏感数据或生产配置时遵守安全与日志约束。
3. 假设门：基于证据提出可验证假设，避免一次性堆叠多个未知变量。
4. 验证门：按最小实验验证假设，每次只改变一个关键条件；涉及高风险操作时先说明影响和回滚方式。
5. 报告门：定位根因后给出修复方案、回归验证方式、命中的关键约束和剩余风险。
6. 沉淀门：仅将可复用经验、长期规则或架构决策沉淀到协议、文档或 Wiki；更新 Wiki 或长期知识库前先询问用户，除非项目协议明确要求。

## WF-RESEARCH research

技术调研默认流程：

1. 预检门：明确调研问题、决策目标、约束、非目标、评估维度和约束触发项。
2. 证据门：优先收集官方文档、项目源码、标准、论文或一手资料；需要最新信息、法律/金融/医疗或高风险准确性时必须验证来源时效。
3. 对比门：对比候选方案的适配性、成本、风险、维护性和迁移影响；涉及项目采用建议时关联项目约束或工程路由。
4. 事实门：区分已验证事实、合理推断和待确认信息。
5. 报告门：给出推荐结论、适用范围、验证建议、命中的关键约束和后续决策点。
