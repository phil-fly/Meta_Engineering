# 场景手册

本文件是技能内场景流程的单一来源。落盘到目标仓时，先确认场景手册真值源：新项目默认使用 `ai-agent-workspace/protocols/playbooks/` 并按章节拆分为独立文件；旧项目可兼容 `ai-agent-protocols/playbooks/`。若目标仓已有根级 `playbooks/` 并明确继续作为真值源，则协议包内只生成索引或别名说明，不复制完整正文。

## WF-CODING coding

开发任务默认流程：

1. 识别语言、工程域和风险等级。
2. 先读 `../engineering/index.md`，再读取对应工程路由。
3. 检查是否涉及 API、数据结构、配置、权限、安全、性能、日志、用户可见文案或架构边界；涉及运行配置、功能配置或外部集成配置时，必须读取配置可发现性规则；涉及安全、错误日志、国际化、通用质量或性能时，分别补读 `../engineering/security/index.md`、`../engineering/core/error-and-logging.md`、`../engineering/frontend/i18n-governance.md`、`../engineering/core/common-quality.md` 或 `../engineering/performance/index.md`。
4. 按最小修改实施。
5. 运行与变更范围匹配的验证。
6. 汇报变更、验证结果和剩余风险；若涉及协议维护或规则变更，按 `../checks/checklists.md` 的 `CHK-MAINT-*` 闭环；若产生可复用经验、长期设计模式或架构决策，先询问用户是否沉淀到 Wiki。

## WF-ARCHITECTURE architecture

架构任务默认流程：

1. 明确目标、约束、非目标和影响范围。
2. 读取相关工程路由和通用质量、安全、性能路由。
3. 对比可选方案及权衡。
4. 给出推荐方案、迁移影响和验证方式；若产生可复用经验、长期设计模式或架构决策，先询问用户是否沉淀到 Wiki。

## WF-ENTERPRISE-SAAS-DESIGN enterprise-saas-design

企业级 SaaS、管理后台、控制台、运维平台、安全平台、云管平台、AI 平台、数据平台或设备管理系统的产品与页面设计默认流程：

1. 先判断任务是否属于企业级产品设计；官网、活动页、品牌宣传、营销落地页、游戏化界面或纯概念稿不使用本流程。
2. 读取 `../engineering/frontend/enterprise-saas-design.md`，并按页面类型补读紧凑布局、UI 稳定性、组件系统、表格列表、表单、Design Token、可访问性和测试相关路由。
3. 完成产品建模，至少输出系统类型、核心实体、用户角色、核心流程、辅助流程、关键状态和用户真正管理的对象。
4. 设计信息架构，按用户目标、业务流程和业务领域组织一级菜单、二级菜单、菜单职责、用户入口和核心操作。
5. 为每个关键页面定义页面目标、主要操作、次要操作、管理实体、关键决策、前置条件和后置结果。
6. 根据页面职责推导布局和组件，覆盖 Dashboard、管理页面、编辑页面、巡检中心或项目特定页面结构。
7. 先输出线框图，再输出视觉设计 Prompt 或高保真设计稿；用户明确只要局部产物时，保留必要前置结论并说明省略项。
8. 使用 `../checks/checklists.md` 的 `frontend-enterprise-saas-design-checklist` 验收，说明已覆盖项、未覆盖项和剩余风险。

## WF-SECURITY-REVIEW security-review

安全审查默认流程：

1. 声明审查模式、范围、未覆盖范围和资产边界。
2. 读取 `common-security.md`、`auth-and-permission.md`、相关语言路由和相关业务路由；涉及配置或历史实现检查时补读 `dependency-and-config.md`；如项目协议声明专用影响面工具，优先用于盘点入口、数据流、身份、资源、敏感操作和外部依赖，不可用时说明限制并用源码搜索、日志或测试结果替代。
3. 先盘点入口、数据流、身份、资源、敏感操作、外部依赖和配置入口。
4. 按控制点审查，避免只凭漏洞直觉搜索。
5. 按 `../checks/checklists.md` 的 `CHK-SEC-*` 自检后，输出发现、证据、影响、修复建议和沉淀去向。

## WF-PERFORMANCE-REVIEW performance-review

性能审查默认流程：

1. 声明审查范围、关键路径和性能目标。
2. 读取 `common-performance.md`、相关语言路由、数据访问和可观测性路由；如项目协议声明专用影响面工具，优先用于盘点关键路径、调用链、数据访问和外部依赖，不可用时说明限制并用源码搜索、日志或测试结果替代。
3. 检查 N+1、资源泄漏、复杂度、对象分配、阻塞和缓存一致性。
4. 按 `../checks/checklists.md` 的 `CHK-PERF-*` 自检后，输出瓶颈、证据、优化建议、验证方式和风险。

## WF-TROUBLESHOOTING troubleshooting

故障排查默认流程：

1. 明确现象、影响范围、发生时间、复现条件和最近变更；若项目协议声明本地调试记忆文件，先读取该文件获取固定调试环境信息。
2. 收集日志、错误信息、配置、输入输出、环境差异和相关代码证据。
3. 基于证据提出可验证假设，避免一次性堆叠多个未知变量。
4. 按最小实验验证假设，每次只改变一个关键条件。
5. 定位根因后给出修复方案、回归验证方式和剩余风险。
6. 仅将可复用经验、长期规则或架构决策沉淀到协议、文档或 Wiki。

## WF-RESEARCH research

技术调研默认流程：

1. 明确调研问题、决策目标、约束、非目标和评估维度。
2. 优先收集官方文档、项目源码、标准、论文或一手资料。
3. 对比候选方案的适配性、成本、风险、维护性和迁移影响。
4. 区分已验证事实、合理推断和待确认信息。
5. 给出推荐结论、适用范围、验证建议和后续决策点。
