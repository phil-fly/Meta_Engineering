# 问题台账与修复方案

本文件定义排障结果如何落盘、进入修复、验证和关闭。它是执行契约，不替代目标仓库的业务 Spec、ADR 或外部 Issue 系统。

## 真值源

问题台账只能有一个可编辑真值源：

- 新项目默认使用 `ai-agent-workspace/issues.md`。
- 已有根级 `issues.md` 时，继续使用根级文件作为兼容真值源。
- 项目若已经声明其他台账路径，按项目协议执行，并在协议中明确映射。
- GitHub、Jira、Linear 等外部系统只作为关联记录，除非项目明确指定其为唯一真值源。
- 不得同时维护两份可编辑的问题正文；兼容文件只能是入口、映射或别名。

问题台账不是生成报告，也不是长期知识库。它记录需要跟踪的发现、修复决策和验证证据；可复用经验、架构决策和长期规则按 `CON-KNOWLEDGE-CAPTURE` 另行沉淀。

## 约束

### CON-ISSUE-001 问题发现必须落盘

- 适用范围：故障排查、审查、调研或开发中产生的可执行问题。
- 生效条件：发现需要修复、跟踪、验证或明确决策的问题时。
- 流程节点：`WF-TROUBLESHOOTING` 证据门、报告门；相关 `WF-CODING` 预检门。
- 门禁动作：解析项目声明的问题台账路径；没有可用台账时按统一布局创建默认台账；为每个可执行发现分配稳定 ID，并记录影响、证据和当前状态。
- 规则正文：可执行问题必须进入问题台账；仅限当前实验且不需要跟踪的观察可以留在任务记录中，但报告必须说明其未进入台账的原因。
- 验证方式：检查问题 ID、状态、影响范围、证据和关联路径是否存在于唯一真值源。
- 报告要求：最终报告引用问题 ID，并对未落盘的发现说明排除理由。
- 例外/优先级：用户当前明确指定的外部唯一真值源优先；安全、数据完整性和平台边界不可覆盖。

### CON-ISSUE-002 修复前必须有方案

- 适用范围：对已确认问题实施代码、配置、数据或架构修复。
- 生效条件：问题状态准备从 `confirmed` 进入 `in_progress`，或开始任何可能改变行为的修复动作前。
- 流程节点：`WF-TROUBLESHOOTING` 方案门；`WF-CODING` 变更门；高风险变更补充影响分析和确认。
- 门禁动作：在问题条目中补齐修复目标、范围、拟改动、风险、回滚方式、验证方式和 Spec/ADR 影响；方案不完整时停止实施。
- 规则正文：修复前必须存在可审阅的修复方案；低风险方案可直接写在问题条目中，中高风险或跨域方案可关联独立文档，但问题条目仍必须保留摘要和链接。
- 验证方式：检查状态为 `planned`，方案字段完整，且高风险项具备影响、回滚和确认记录。
- 报告要求：实施报告引用方案版本或问题条目中的方案内容，并说明未更新 Spec/ADR 的理由（如适用）。
- 例外/优先级：只读诊断、临时观测和不改变系统行为的实验不进入 `in_progress`，但不得借此绕过修复门禁。

### CON-ISSUE-003 关闭必须有验证证据

- 适用范围：问题关闭、拒绝、去重或延后处理。
- 生效条件：准备结束问题生命周期时。
- 流程节点：`WF-TROUBLESHOOTING` 验证门、报告门；相关 `WF-CODING` 验证门。
- 门禁动作：回填验证命令或运行证据、结果、验证范围和剩余风险；只有验证通过的问题才能进入 `closed`。
- 规则正文：不得以“已修改”或“测试已运行”替代问题验证；无法验证时必须改为 `deferred` 或其他明确的非关闭状态。
- 验证方式：问题条目存在可复核的验证证据，且证据覆盖声明的影响范围。
- 报告要求：最终报告说明已关闭、延后、排除、重复和后续任务的数量与问题 ID。
- 例外/优先级：用户明确接受风险并选择延后时，记录接受者、范围和复查条件，不得标记为 `closed`。

### CON-ISSUE-004 发现必须可对账

- 适用范围：一次排障、审查或修复任务中的全部问题发现。
- 生效条件：报告、审查或任务结束前。
- 流程节点：相关 `WF-*` 报告门和 `Completion Gate`。
- 门禁动作：将每条发现归类为 `closed`、`deferred`、`rejected`、`duplicate` 或后续任务，并确保报告、台账和修复方案中的数量一致。
- 规则正文：问题不得从输出中静默消失；未确认的候选问题也要保留状态或明确排除。
- 验证方式：逐条核对发现、问题 ID、状态和报告归类；检查没有无主的修复动作或无来源的关闭记录。
- 报告要求：最终回复按已解决、延后处理、明确排除和转入后续任务闭环。
- 例外/优先级：纯信息性观察可不建问题条目，但必须在报告中列为不适用并说明原因。

## 状态流转

```text
candidate → investigating → confirmed → planned → in_progress → verified → closed
                         ├→ rejected
                         ├→ duplicate
                         └→ deferred
```

- `candidate`：已记录但证据尚不足。
- `investigating`：正在收集证据或验证假设。
- `confirmed`：根因或问题影响已得到足够证据支持。
- `planned`：修复方案已完成，可进入实施。
- `in_progress`：修复已经开始。
- `verified`：修复后的回归验证已通过，等待回填关闭记录。
- `closed`：证据、剩余风险和关联变更均已完整记录。
- `deferred`：明确延后，必须记录原因、责任边界和复查条件。
- `rejected`：证据不足或确认不构成问题，保留判断依据。
- `duplicate`：与已有问题合并，必须关联主问题 ID。

## 最小条目契约

每个可执行问题至少记录：

- 稳定 ID、标题、状态、严重度和首次发现时间。
- 现象、影响范围、复现条件和证据链接。
- 根因或当前假设，并区分已确认与待验证内容。
- 修复目标、范围、拟改动、风险、回滚方式和验证方式。
- 实施结果、验证结果、剩余风险和关联代码、Spec、ADR、PR 或后续任务。

低风险问题可以在同一条目中完成方案；中高风险或跨域问题可以关联独立方案文档，但问题台账仍是状态和结果的索引真值源。
