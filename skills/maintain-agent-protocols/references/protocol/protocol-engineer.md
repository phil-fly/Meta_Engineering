# Protocol Engineer

## Mission

负责设计、审查和优化 AI 协作协议体系。

目标：

- 提高 Agent 执行一致性。
- 降低协议复杂度。
- 减少规则冲突。
- 提升长期可维护性。

## 适用场景

- 用户要求审查、优化或重构 AI 协作协议体系。
- 用户提到 `Protocol Engineer`、协议复杂度、规则冲突、执行率、Token 成本或长期维护性。
- 需要判断内容应放入用户协议、项目协议、场景手册、模板、Spec 或 Wiki。

## 审查流程

1. 声明检查范围、未检查范围和结论适用范围。
2. 收集协议入口、工程路由、场景手册、模板、Spec、Wiki 和项目级文档。
3. 按审查维度逐项分析，并引用具体文件或章节证据。
4. 输出问题分级、影响范围和建议方案。
5. 将发现归类为已解决、延后处理、明确排除或转入后续任务。

## 1. 角色定位

检查用户级协议、项目级协议、场景手册和模板是否混杂。

原则：

```text
用户协议负责原则
项目协议负责约束
场景手册负责执行
模板负责格式
```

典型问题：

- 用户协议写入具体命令、长流程或检查清单。
- 项目协议重复用户级通用原则。
- 场景手册混入稳定项目事实。
- 模板承载决策规则，而不是格式骨架。

## 2. 协议膨胀

检查：

- 重复规则。
- 冗余说明。
- 教程内容。
- 示例内容。

原则：

```text
规则 ≠ 文档
规则 ≠ 教程
```

判断：

- 必须长期遵守的内容保留为规则。
- 解释性背景移入文档或删除。
- 可复用流程沉淀为 Playbook。
- 可复用格式沉淀为 Template。

## 3. 执行率分析

评估：

- Agent 是否容易理解。
- Agent 是否容易遵循。
- 是否存在长距离依赖。
- 是否存在隐式约束。

输出：

```text
高执行率
中执行率
低执行率
```

判定参考：

- 高执行率：入口清晰、路径短、规则可执行、无隐式前提。
- 中执行率：规则基本清晰，但需要跨文件推断或存在少量重复。
- 低执行率：入口分散、职责混杂、存在长距离依赖或隐式约束。

## 4. 冲突分析

检查：

- 规则冲突。
- 优先级冲突。
- 工作流冲突。

输出：

```text
冲突项
影响范围
建议方案
```

处理原则：

- 高优先级规则覆盖低优先级规则。
- 通用规则保留在用户级或路由层。
- 项目例外保留在项目级协议。
- 无法判断时标注冲突，不静默选择。

## 5. 结构分析

检查以下资产职责是否清晰：

```text
AGENTS.md
Playbook
Template
Spec
Wiki
```

职责建议：

- `AGENTS.md`：入口、优先级、任务分类、长期原则。
- `Playbook`：任务执行方法和闭环流程。
- `Template`：可复用输出格式或文件骨架。
- `Spec`：业务能力、接口、数据结构、权限和架构约束。
- `Wiki`：长期知识、设计背景和可复用经验。

## 6. Token 成本分析

评估：

- 文件长度。
- 重复内容。
- 长期上下文成本。

输出：

```text
当前长度
建议长度
压缩率
```

压缩率计算：

```text
压缩率 = (当前长度 - 建议长度) / 当前长度
```

建议：

- 用户协议只保留高频入口和长期原则。
- 低频细节下沉到 `routes/`、`playbooks/`、`checks/` 或 `templates/`。
- 重复路径可使用少量稳定变量，但不要引入需要心算的复杂别名。

## 7. 演进建议

判断：

- 是否应拆分。
- 是否应沉淀为 Playbook。
- 是否应沉淀为 Template。
- 是否应沉淀为 Spec。
- 是否应沉淀为 Wiki。

输出建议时说明：

- 建议动作。
- 目标位置。
- 迁移理由。
- 风险和验证方式。
