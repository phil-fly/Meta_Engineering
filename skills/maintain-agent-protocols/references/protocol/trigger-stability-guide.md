# 触发稳定性指南

本文件用于审查和强化协议包中的触发链路。它定义人工或半结构化审查方法，不承诺存在自动验证引擎、持久化数据模型或配置文件；没有脚本时，结论必须来自已读取文件、`rg` 搜索结果或明确标注的待确认推断。

## 适用场景

- 用户要求“触发稳定性审查”“执行率审查”“约束总是漏触发”“技能输出不稳定”。
- 创建或升级协议包时，需要检查新规则是否能被真实任务流程触达。
- Protocol Engineer 审查中发现项目级约束、条件适用路由或检查项依赖 Agent 自行记忆。

## WF-PROTOCOL-TRIGGER-STABILITY 核心链路

按以下链路检查每条规则是否可触达。

```text
用户任务表达
→ 任务分类 / 生效入口
→ 场景手册 WF-*
→ 工程路由 routes/**
→ 项目约束 CON-*
→ 检查清单 CHK-*
→ 最终报告闭环
```

审查时分别记录：

- 工作流是否能从任务分类或入口表稳定触发。
- 场景手册是否说明何时读取工程路由。
- 条件适用路由是否有触发条件，而不是只写“条件适用”。
- 项目级约束是否有生效条件、验证方式和短路径引用。
- 闭环步骤是否能定位到相关检查清单或检查项编号族。

## 稳定性分级

- `高稳定`：入口真实存在，触发条件明确，相关场景手册或路由中有短路径引用；执行者不需要跨多个文件自行推断。
- `中稳定`：规则正文清楚，但需要通过项目协议、路由索引或任务经验推断；缺少 playbook 级显式触发或检查项映射。
- `低稳定`：路径悬空、触发条件模糊、只在项目协议中孤立出现，或高风险约束没有被相关工作流触达。

风险分级：

- `一级风险`：安全、权限、删除、敏感数据、审计、数据迁移、发布、外部状态或高风险工具使用可能漏触发。
- `二级风险`：质量、性能、配置、日志、国际化、可访问性等条件适用规则需要模型推断。
- `三级风险`：低频治理、报告格式或建议类规则缺少直接触发，但不影响关键行为正确性。

## 审查流程

1. 声明范围：检查了哪些入口、playbooks、routes、checks、项目协议和模板；没有读取的范围必须列出。
2. 扫描编号：用 `rg "WF-|CON-|CHK-"` 或等价方式提取工作流、约束和检查项编号，记录来源位置。
3. 扫描引用：检查 playbooks 是否引用必要路由、约束编号或检查项编号族；检查 routes/index 是否说明条件适用触发。
4. 分级判断：按高/中/低稳定和一/二/三级风险输出清单；证据不足时标为待确认。
5. 给出强化建议：优先建议最短可维护引用，不复制完整约束正文。
6. 闭环归类：所有发现归入已解决、延后处理、明确排除或转入后续任务。

可用搜索示例：

```bash
rg -n "WF-|CON-|CHK-" AGENTS.md ai-agent-workspace/protocols ai-agent-protocols playbooks
rg -n "条件适用|项目证据支持|通用治理" ai-agent-workspace/protocols/routes ai-agent-protocols/routes
```

## 强化规则

`CON-TRIGGER-NO-FULL-DUPLICATE`：不要把项目约束原文复制到多个 playbooks。强化触发链路时，只写触发条件、目标路由或约束编号引用。

`CON-TRIGGER-SHORTEST-LINK`：优先在最接近任务入口的位置补一行短引用。例如开发任务中的安全、配置、日志、国际化和性能触发，优先放入 `WF-CODING` 的路由判断步骤；审查任务中的工具和检查项，优先放入对应审查 playbook。

`CON-TRIGGER-PATH-REAL`：新增引用必须使用目标仓已存在、将生成或已声明兼容映射的真实路径；禁止写悬空的 `@routes`、`@checks` 或抽象路径。

`CON-TRIGGER-CONDITIONAL-ROUTE`：条件适用路由至少在路由索引或路由正文中说明触发条件；高风险或高频条件路由还应在相关 playbook 中有短触发语句。

`CON-TRIGGER-PROJECT-CONSTRAINT`：项目级约束若会影响开发、审查、排障或发布流程，应在相关 playbook 中引用约束编号或触发路由；若只是项目事实或低频说明，可保持在项目协议中，不强制进入 playbook。

`CON-TRIGGER-CHECK-MAPPING`：playbook 闭环步骤应映射到相关检查清单或编号族，例如安全审查映射 `CHK-SEC-*`，性能审查映射 `CHK-PERF-*`，协议维护映射 `CHK-MAINT-*`。不需要在 playbook 中列出完整清单。

`CON-TRIGGER-OPTIONAL-STRENGTHENING`：协议升级同步时，触发稳定性审查默认只读执行；强化 playbooks、routes 或 checks 属于可选变更，必须在升级预览中列出拟修改文件并获得用户确认。新建协议包时，可把通用触发规则直接写入新生成的 playbooks，但仍需在预览中声明。

## 典型强化位置

| 发现 | 建议位置 | 写法原则 |
| --- | --- | --- |
| 安全、权限、敏感数据、删除、审计等约束漏触发 | 开发、安全审查或架构 playbook 的路由判断步骤 | 写触发条件和安全路由路径，不复制安全清单 |
| 条件适用路由只在 routes/index 标注 | 对应路由正文或相关 playbook | 补“涉及 X 时读取 Y” |
| 工具使用约束只在项目协议中 | 对应审查 playbook | 写优先使用条件、不可用时降级说明和报告限制 |
| Wiki 或长期知识沉淀约束漏触发 | 开发、架构、排障闭环步骤 | 写“产生可复用经验时先询问用户” |
| 检查清单没有进入闭环 | 对应 playbook 的最后输出步骤 | 引用检查清单文件或 `CHK-*` 编号族 |

## 验证

- 新增或修改引用后，使用 `rg` 确认编号、路径和检查项引用可达。
- 修改 playbooks 后，确认没有复制完整约束正文、没有引入不存在路径、没有让单一步骤过长。
- 协议包生成或升级报告中说明触发稳定性变化；无法量化时说明“基于本轮已读文件的定性判断”。
