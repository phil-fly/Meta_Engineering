# 依赖与安全配置

依赖和配置必须遵循最小暴露、可追踪和失败关闭原则。

## 核心规则

- 依赖必须跟踪版本和漏洞风险，高危漏洞应及时升级或记录例外。
- 禁止使用默认凭证、调试端点、详细生产错误和不必要功能。
- 安全配置无法解析或缺失时必须失败关闭，不得默认放行。
- 安全头、CORS、网关策略、认证前置和环境差异必须显式可审查。
- 配置样例不得包含真实密钥、连接串、令牌或私有地址。

## CON-CONFIG-001 配置可发现性（Configuration Discoverability）

适用范围：开发阶段新增或修改影响系统运行、功能启用或外部集成的配置项。

生效条件：涉及用户需要完成、维护或排查的运行关键配置、功能配置、外部集成配置时。

配置等级：

- P0 运行关键配置：例如 License、API Key、数据库连接、OAuth、SMTP、Overlay 网络参数。必须满足安装向导、首次启动配置向导或 UI 配置页面之一。
- P1 功能配置：例如策略规则、阈值参数、服务集成配置。必须提供 UI 配置入口或配置管理 API。
- P2 开发调试配置：例如 DEBUG、TRACE、PPROF。允许通过环境变量或配置文件管理。

规则正文：

- 任何影响系统运行、功能启用或外部集成的配置项，必须具备产品内可发现的配置入口。
- 禁止将用户必须配置的参数仅暴露于 README、安装手册、环境变量、配置文件、启动参数或数据库初始化脚本。
- P0、P1、P2 配置必须按配置等级要求提供对应入口或管理方式。

禁止事项：

- 禁止功能依赖手册中的额外配置步骤。
- 禁止功能依赖隐藏环境变量。
- 禁止功能依赖修改容器启动参数。
- 禁止功能依赖修改宿主机配置文件。
- 禁止功能上线后用户无法从产品界面发现相关配置。

以上情况均视为设计缺陷。

评审要求自检：

1. 用户在哪里完成配置？
2. 用户如何发现该配置？
3. 配置是否支持审计？
4. 配置是否支持导出备份？
5. 如果未配置，系统如何提示？

验证方式：

- 设计评审必须逐项完成评审要求自检。
- 开发实现必须检查配置入口、权限控制、审计记录、导出备份能力、未配置状态提示和文档说明是否一致。
- 历史实现审查必须检查既有配置是否仅存在于 README、环境变量、配置文件、启动参数、初始化脚本或宿主机文件中；如是，必须标记为配置可发现性缺口或说明 P2 例外依据。

例外/优先级：仅 P2 开发调试配置可不提供产品内配置入口；若上层用户要求、项目规范或安全限制要求更高等级配置入口，以上层要求为准。

## 输出要求

- 说明依赖风险、配置默认值、配置入口、失败行为和例外依据。
