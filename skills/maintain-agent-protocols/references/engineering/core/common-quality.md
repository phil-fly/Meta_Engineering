# Common Quality

适用命名、状态语义、注释规范、重构、引用清理、占位数据和根因修复。

核心规则：

- 共享标识符跨前后端、接口、权限、页面和配置时必须使用稳定一致命名。
- 变更名、目录名和规则名应稳定、可检索、机器友好。
- 优先编写自解释代码：使用清晰的变量名、方法名、函数名和类型名表达意图，而不是依赖注释解释代码字面行为。
- 禁止添加重复代码含义的注释，例如“初始化变量”“返回结果”“调用 save() 方法保存数据”。
- 注释仅用于复杂算法、非显而易见的业务逻辑、兼容性约束、协议要求、边界条件和设计取舍，优先解释“为什么”而不是“做了什么”。
- 共享术语避免中英文混搭，选择单一稳定语言表达。
- 变量和派生状态必须定义清楚语义、拥有者和默认态。
- 删除或重构后不得留下 route、menu、import、handler、配置、文档入口等悬空引用。
- 未接通能力时应暴露真实状态，禁止用伪数据占位掩盖集成缺口。
- 修复必须回到初始化、约束、契约或算法根因，避免宽泛吞错、静默兜底和硬编码特判。
- 新增或替换实现前应先搜索既有实现、组件、服务、工具函数和项目模式；若不复用，应说明差异、约束或迁移成本。
- 已验证且仍符合需求的公共交互骨架应优先复用；如果旧抽象已不适用，应说明扩展或替换理由。
- 页面或流程改造前必须确认真实挂载入口。
- 列表型重构必须先对齐主查询模型。
- 用户可感知多步流程必须有可执行验收路径。

验证与输出：

- 说明命名、注释、状态、引用、占位数据和根因修复是否合格。
- 说明是否搜索过已有实现，以及复用、扩展或新建的理由。
- 对未解决项给出延后、排除或后续任务分类。
