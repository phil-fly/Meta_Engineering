# 时间与时区

## 适用场景

- 需求、数据模型、API、前端展示、导出报表、部署配置或测试涉及时间点、日期、时长、时区、超时、过期、定时或时间范围时读取本路由。
- 需求讨论阶段先使用本路由区分业务语义；进入实现或审查阶段继续保留对应约束引用。

## 路由状态

```text
状态：通用治理
证据：跨存储、API、前端、导出、部署和测试边界的通用时间语义
适用条件：命中时间字段、时间参数、日期、时长、时区、超时、定时、过期或时间范围
```

核心口令：先区分 Instant、Date、Duration；时间点统一 UTC 入库，RFC3339 带时区出 API，展示与导出在边界按明确时区转换。

## 核心规则

### CON-TIME-001 时间语义先分类

- 适用范围：需求、数据模型、API、表单和报表字段定义。
- 生效条件：新增或修改任何日期/时间字段、时间参数或时间范围。
- 流程节点：`WF-ARCHITECTURE` 预检门；`WF-CODING` 预检门。
- 门禁动作：先标记字段是绝对时间点（Instant）、业务日期（Date）还是持续时长（Duration），再选择存储和传输类型；时间范围还必须分别标记端点语义、开闭区间和空值语义。
- 规则正文：Instant、Date 和 Duration 必须分开建模；业务日期使用 `YYYY-MM-DD`，不得为了复用时间点格式强行转换为 UTC；Duration 必须携带明确单位，不得伪装成时间点。准备把无时区本地日期时间作为 Instant 时，必须先从需求、契约、现有实现或调用方确认时区来源，仍无法确定时必须请求确认，不得根据字段名、服务器位置或开发者所在地猜测。
- 验证方式：检查字段定义、DTO/schema、表单输入、示例数据和调用方是否能表达完整语义与时区来源。
- 报告要求：说明字段分类、时区来源和未确定的业务语义。
- 例外/优先级：项目 Spec、业务法规或上层平台契约可以定义更具体的语义，但不得把不同语义混成同一字段。

### CON-TIME-002 存储统一表示绝对时间点

- 适用范围：数据库、缓存、事件、任务和持久化模型。
- 生效条件：存储绝对时间点或可跨服务比较的时间值。
- 流程节点：`WF-ARCHITECTURE` 设计门；`WF-CODING` 变更门；`WF-TROUBLESHOOTING` 证据门。
- 门禁动作：确认存储类型、精度、零值语义和迁移策略，不依赖服务器本地时区。
- 规则正文：绝对时间点必须以 UTC instant 统一保存；存储类型和 ORM 映射必须在数据库会话时区变化时仍保持同一时刻。使用 Unix timestamp 时必须明确秒或毫秒等单位与精度；禁止保存依赖服务器本地时区的无时区日期时间。
- 验证方式：检查 schema、ORM 映射、序列化边界、数据库会话时区和迁移脚本。
- 报告要求：说明存储表示、精度、零值处理和迁移影响。
- 例外/优先级：业务日期和持续时长不适用，但必须分别使用日期类型和带明确单位的 duration 表达。

### CON-TIME-003 API 时间必须携带时区

- 适用范围：HTTP/JSON API、事件、DTO、请求参数和响应体。
- 生效条件：接口传输绝对时间点。
- 流程节点：`WF-ARCHITECTURE` 设计门；`WF-CODING` 变更门和验证门。
- 门禁动作：确认请求和响应的时间格式由共享序列化入口处理，并检查兼容策略。
- 规则正文：绝对时间点 API 必须使用带 `Z` 或显式偏移量的 RFC3339 表达；禁止跨 API 边界返回 `YYYY-MM-DD HH:mm:ss` 这类无时区日期时间；所有 DTO 应复用同一时间格式化/解析入口。
- 验证方式：检查 OpenAPI/schema、DTO serializer、请求校验、契约测试和错误路径。
- 报告要求：说明输入输出格式、兼容策略和是否存在旧无时区字段。
- 例外/优先级：业务日期使用 `YYYY-MM-DD`；持续时长使用明确的数值单位或标准 duration 表达，不伪装成时间点。

### CON-TIME-004 展示按明确的用户或业务时区转换

- 适用范围：Web/移动端展示、客户端格式化和用户可见时间字段。
- 生效条件：将 API 时间点转换为用户可见文本。
- 流程节点：`WF-CODING` 变更门和验证门。
- 门禁动作：先确认展示语义是浏览器本地时区、用户偏好时区还是业务固定时区，并确认来源，再复用共享 formatter。
- 规则正文：只有展示策略明确采用浏览器本地时区时，才使用浏览器标准 Date/Intl 等机制解析和格式化；用户偏好或业务固定时区必须显式传入。禁止手动固定加减小时、默认假设用户处于某个时区或由页面各自实现时间格式化。
- 验证方式：检查共享 formatter、时区来源、浏览器本地设置和跨日期边界展示。
- 报告要求：说明展示时区来源、格式化入口和未覆盖的用户时区。
- 例外/优先级：审计、结算、排班等业务显示可以优先使用业务时区，但必须在需求或项目规范中明确声明。

### CON-TIME-005 导出和报表使用显式业务时区

- 适用范围：CSV、Excel、PDF、报表、批量导出和离线任务。
- 生效条件：导出或生成不依赖浏览器环境的时间文本。
- 流程节点：`WF-CODING` 变更门和验证门；`WF-SECURITY-REVIEW` 相关审查门。
- 门禁动作：确认业务时区配置、非法配置行为、导出字段语义和审计范围。
- 规则正文：导出和报表必须使用明确的 IANA 业务时区或契约明确的 UTC，不得隐式继承运行机器或调用者时区；非法时区必须报错，配置缺失时必须使用已声明业务含义的默认值或显式失败，禁止静默回退到机器时区；面向人阅读的时间应带偏移量，机器消费字段应保留可解析的 UTC 或等价绝对时间值。
- 验证方式：使用固定时间验证导出文本、偏移量、非法时区、配置缺失和显式默认值路径。
- 报告要求：说明业务时区来源、失败行为、导出格式和权限/审计影响。
- 例外/优先级：项目规范可以为特定报表声明不同业务时区，但必须按报表或业务域明确配置。

### CON-TIME-006 部署不得依赖机器时区

- 适用范围：服务启动、容器镜像、定时任务、运行配置和升级脚本。
- 生效条件：服务或离线任务需要业务时区、格式化时区或 zoneinfo 数据。
- 流程节点：`WF-ARCHITECTURE` 设计门；`WF-CODING` 变更门和报告门。
- 门禁动作：确认业务时区配置入口、默认值、升级保留策略和运行时 zoneinfo 可用性。
- 规则正文：业务时区必须通过显式配置或已声明业务含义的默认值提供，禁止依赖部署机器的本地时区；使用 IANA 时区的运行时必须包含可用的时区数据库（Go 等依赖运行时 zoneinfo 的后端也适用）；升级脚本补充新配置时不得覆盖用户已有配置。
- 验证方式：检查容器/镜像、启动参数、环境变量、配置迁移和精简运行时。
- 报告要求：说明配置来源、默认/缺失行为、zoneinfo 依赖和升级兼容性。
- 例外/优先级：仅处理 UTC instant 且不产生业务本地时间的进程可以不配置业务时区，但必须说明不适用原因。

### CON-TIME-007 时间比较与计算保持原始语义

- 适用范围：过期、超时、排序、定时、时间范围、日历运算和跨时区计算。
- 生效条件：比较时间先后、计算持续时间，或按本地日历规则推导下一时刻。
- 流程节点：`WF-ARCHITECTURE` 设计门；`WF-CODING` 变更门和验证门；`WF-TROUBLESHOOTING` 假设门和验证门。
- 门禁动作：确认运算对象是 Instant、Date 还是 Duration，并区分绝对时长运算与业务日历运算。
- 规则正文：Instant 必须按绝对时间比较，不得比较格式化后的本地时间字符串；超时和耗时应基于原始 Instant 或 Duration 计算。按业务日历进行跨日、跨月、跨年或定时计算时必须使用明确的 IANA 时区和时区感知库，并为 DST 开始时不存在的本地时间与结束时重复的本地时间定义处理策略；禁止用固定 UTC Offset 替代需要 DST 规则的时区。
- 验证方式：验证等价偏移时间点、跨日期边界、DST 跳变和重复时刻的比较与计算结果。
- 报告要求：说明运算语义、时区、DST 策略和未覆盖边界。
- 例外/优先级：纯 Date 比较可使用日期类型，纯 Duration 比较可使用带明确单位的 duration；二者不得先伪造成 Instant 再比较。

### CON-TIME-008 跨时区测试必须覆盖边界

- 适用范围：时间解析、序列化、展示、导出、定时和时间范围计算的测试。
- 生效条件：新增或修改时间相关行为，或修复时间/时区缺陷。
- 流程节点：`WF-CODING` 验证门；`WF-TROUBLESHOOTING` 验证门。
- 门禁动作：使用固定 UTC 时间，并覆盖与变更相关的 UTC、非 UTC、DST、零值、空值、日期边界、非法格式和非法时区。
- 规则正文：测试不得只验证“后端输出等于后端输入”；必须验证时间语义在存储、API、解析、时区转换、展示、导出或定时边界之间保持正确。涉及跨时区转换、定时或导出时，时区矩阵至少包含 `UTC`、`Asia/Shanghai`、`America/New_York` 和 `Europe/London`，并覆盖 DST 不存在和重复的本地时刻；固定样例应验证 `2026-09-29T07:14:34Z` 在 `Asia/Shanghai` 显示为 `2026-09-29 15:14:34`。
- 验证方式：运行 unit、契约、集成或 E2E 测试，并记录所覆盖时区、DST、零值/空值、非法输入和非法配置。
- 报告要求：说明测试层级、时区矩阵、未覆盖边界和剩余风险。
- 例外/优先级：纯业务日期或纯 duration 测试可不引入时区，但仍需验证其不会被误转为时间点。

## 验证与输出

- 需求阶段：输出每个时间字段的语义、时区来源、边界转换和待确认项。
- 实现阶段：说明存储、API、展示、导出、部署、计算和测试分别命中了哪些 `CON-TIME-*`。
- 审查阶段：按 `CHK-TIME-*` 逐项报告已覆盖、未覆盖、明确排除和剩余风险。
